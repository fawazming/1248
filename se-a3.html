CSC 715 Answers 3 - L5 Requirements II + L6 Modeling

SE-L5Q1 Structure of the requirements document

Preface (readership, history), Introduction, Glossary, User Requirements, System Architecture, System Requirements Specification, System Models, System Evolution, Appendices, Index. Different readers need different sections.

SE-L5Q2 Natural language specification

Advantages: expressive, understood by all, no special training. Disadvantages: ambiguity, over-flexibility, no modularity, mixed levels. Guidelines: standard format, consistent shall/should, highlight key parts, avoid jargon, add a rationale.

SE-L5Q3 Three stages of change management

  1. Problem analysis and change specification - validate the change.
  2. Change analysis and costing - assess impact (traceability) and cost.
  3. Change implementation - update requirements, design, code.

SE-L5Q4 Requirements traceability

Following a requirement from origin through design, implementation and testing, and seeing links between requirements. Important for impact assessment, completeness checks and test coverage.

SE-L5Q5 Tools in requirements management

Store requirements, manage versions, change control, traceability links and reports. Functions: unique IDs, attributes (priority/status/source), linking, change workflows, query/reporting.

SE-L6Q1 Four UML system perspectives

  1. External - context/environment (use-case or context diagram).
  2. Interaction - interactions (sequence or activity diagram).
  3. Structural - organisation/data (class diagram).
  4. Behavioral - dynamic behaviour (state diagram).

SE-L6Q2 Use case diagram

Shows interactions between the system and external actors. Elements: actors (stick figures), use cases (ellipses), links between them. Defines system boundaries and high-level functionality.

SE-L6Q3 Class vs sequence diagram

Class diagram: static structure - classes, attributes, operations, associations; for the object model. Sequence diagram: dynamic message sequence for a scenario; for a specific interaction/use case.

SE-L6Q4 State diagram elements

States (rounded rectangles), transitions (arrows labelled with events), actions/guards. Shows how an object reacts to events over time - its state and what changes it.

SE-L6Q5 Model-driven engineering (MDE)

Models are the primary artefacts; code is generated. For: higher abstraction, platform independence, fewer errors. Against: models may not suit implementation; platform independence only helps long-lived systems; other concerns (requirements, security, testing) often matter more.
